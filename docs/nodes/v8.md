## Timeline

- 2008 — Lars Bak and team at Google Aarhus release V8 alongside Chrome 1.0; first production JIT for JS; Full Codegen emits machine code directly from the AST
- 2009 — [Ryan Dahl](../../people/dahl-ryan.md) takes V8 out of the browser, wraps it with libuv and a module system, ships Node.js; [JavaScript](javascript.md) becomes a server-side language
- 2010 — Crankshaft: SSA optimizer with Hydrogen IR; V8 takes the engine benchmark crown from SpiderMonkey
- 2016 — Ignition (bytecode interpreter) + TurboFan (sea-of-nodes optimizer): a complete architectural rebuild; the two together support deoptimisation properly
- 2017 — [WebAssembly](webassembly.md) lands in V8: Liftoff (baseline WASM JIT) + TurboFan for hot WASM code; WASM is a second frontend, not a second engine
- 2020 — Microsoft Edge switches from Chakra to V8; V8 now runs in every major browser except Firefox (SpiderMonkey) and Safari (JSC)
- 2021 — Sparkplug: a baseline JIT that compiles bytecode to machine code with no IR pass; fills the gap between Ignition and TurboFan
- 2023 — Maglev: mid-tier JIT; the full ladder is Ignition → Sparkplug → Maglev → TurboFan
- 2024 — V8 Sandbox (experimental): heap-cage mechanism to contain JIT exploits within the V8 process

## Ontology

- Four-tier adaptive JIT: Ignition (interpreter) → Sparkplug (baseline, no IR) → Maglev (mid-tier) → TurboFan (top-tier sea-of-nodes); each tier is faster to compile, each later tier produces faster code
- Speculative optimisation: the JIT generates fast code for the types observed so far; deoptimisation is the planned escape when the speculation is wrong — deopt is not failure, it is the mechanism
- Hidden classes and inline caches: V8 retrofits static-type reasoning onto a dynamically-typed language at runtime; monomorphic call sites are fast, polymorphic ones slower, megamorphic ones cliff off
- Single engine for JS and WebAssembly: Liftoff + TurboFan for WASM, Ignition/Sparkplug/Maglev/TurboFan for JS; different frontends, same backend
- Isolate model: each V8 instance is a heap-isolated context; embedders (Node, Electron, Cloudflare Workers) create Isolates — V8 does not define the runtime, only the engine
- Orinoco GC: generational (scavenger for young, concurrent mark-compact for old); pointer compression in 64-bit builds halves heap usage for pointer-heavy workloads

## Demonstrator

V8's speculative-optimisation thesis is proven by `--trace-deopt`: running any hot JS function through the flag shows deoptimisation events with the reason (type change, delete, arguments escape). The deopt log is the thesis made visible — the fast path only exists because the exit path exists.

## Claims

**V8-C001** 🟢 — before V8 (2008) there was no production JIT compiler for JavaScript in any shipping browser; prior engines (SpiderMonkey, JScript) used interpreters

**V8-C002** 🟢 — V8 runs JS and [WebAssembly](webassembly.md) in one engine: Liftoff/TurboFan for WASM, Ignition/Sparkplug/Maglev/TurboFan for JS; WASM shares the same optimising backend, not a separate runtime

**V8-C003** 🟢 — Node.js, Deno, Chrome, Edge (since 2020), Electron, and Cloudflare Workers all embed V8; Google controls the dominant JS engine under a BSD licence, and every major embedder is a separate runtime with different semantics

**V8-C004** 🟡 — V8 plays the same structural role in the web ecosystem as [LLVM](llvm.md) does in systems: a shared optimising backend that benefits any language that targets it (JS, TypeScript, WASM) without exposing its internals

**V8-C005** 🟠 — "V8 makes JavaScript fast" is accurate only for hot monomorphic code; a call site that sees two different receiver shapes (polymorphic) runs slower; one that sees many (megamorphic) falls back to a generic path that erases the benefit of JIT compilation entirely

**V8-C006** 🟠 — JIT compilation is not faster compilation — it is speculation; TurboFan emits fast code for the types it has observed and installs a deopt guard; when the guard trips, V8 throws away the compiled code and falls back to the interpreter; the win is knowing when to give up, not just compiling fast

**V8-C007** 🟠 — V8 is not Node.js, not Chrome, not Electron; it is an embeddable engine with no concept of a DOM, no HTTP stack, no module system; what embedders build around V8 defines the runtime — confusing the engine with the runtime is the single most common V8 misconception

**V8-C008** 🔴 — as WasmGC, WASI threads, and direct DOM access mature: does V8 become a WASM runtime that carries JS as a legacy frontend — or do JS and WASM evolve as co-equal targets of the same engine?
